# Правила разработки CasualtiesCoop

## Основная цель

Разрабатывать стабильный сетевой кооператив для Casualties Unknown с предсказуемой синхронизацией игрового состояния, минимальным вмешательством в ванильную логику и поддерживаемой архитектурой.

Приоритеты: корректность, надёжность, сопровождаемость, производительность, скорость реализации — именно в таком порядке.

## Обязательная документация

Перед изменением соответствующей подсистемы прочитай:

- `docs/architecture.md`
- `docs/network-contract.md`
- `docs/verification.md`
- `docs/coop-plan.md`
- `docs/development-handoff.md`
- Документацию изменяемой игровой механики.

При противоречиях между документацией и реализацией явно зафиксируй расхождение. Не считай устаревшие записи доказательством текущего поведения.

## Архитектура

- Соблюдай SOLID, разделение ответственности и инверсию зависимостей.
- Разделяй сетевой транспорт, сериализацию, авторитетную игровую логику, репликацию и адаптацию к Unity.
- Игровые правила и сетевые state machines должны тестироваться без Unity, Steam и запуска игры.
- Используй композицию вместо наследования, если наследование не отражает реальное отношение типов.
- Используй constructor injection для значимых зависимостей.
- Не используй Service Locator и глобальное изменяемое состояние без обоснованной необходимости.
- Не создавай интерфейс для каждого класса автоматически. Абстракции должны иметь конкретную архитектурную или тестовую ценность.
- Harmony-патчи должны быть тонкими адаптерами. Не размещай в них сложную бизнес-логику.
- Не смешивай авторитетное состояние сущности с Unity GameObject.
- Не дублируй существующие механизмы репликации и восстановления.
- Не вводи универсальные абстракции до появления реальной необходимости.
- Не маскируй God Object разделением на partial-классы.
- При превышении классом 300 строк проверь его ответственность. При превышении 500 строк обоснуй сохранение структуры или предложи декомпозицию.
- Не проводи масштабный несвязанный рефакторинг в рамках исправления отдельного дефекта.

## Стиль C#

- Используй понятные предметные имена.
- Используй ранний выход вместо глубокой вложенности.
- Используй фигурные скобки для управляющих конструкций.
- Соблюдай nullable reference types.
- Не подавляй предупреждения компилятора без объяснения.
- Избегай магических чисел, неявных единиц измерения и необоснованных таймаутов.
- Не используй исключения для штатного управления потоком выполнения.
- Не оставляй пустые catch-блоки.
- Не добавляй комментарии, пересказывающие код. Документируй причины решений, ограничения и инварианты.
- Не используй API, несовместимые с целевой платформой Unity.

## Сетевая корректность

- Для каждого синхронизируемого состояния явно определяй источник истины.
- Проверяй полномочия отправителя, идентификатор сессии и актуальность сообщения.
- Обрабатывай потерю, дублирование, задержку и нарушение порядка сообщений согласно контракту протокола.
- Изменения владения и другие критические операции должны быть идемпотентными.
- Не считай успешную отправку подтверждением выполнения операции.
- Не применяй устаревшие снимки поверх более нового состояния.
- Не допускай повторного появления удалённых сущностей из-за запоздавших сообщений.
- Разделяй авторитетное состояние и клиентское предсказание.
- При отклонении предсказанной операции корректно восстанавливай клиентское состояние.
- Ограничивай размеры сообщений, очередей, коллекций и объём обработки за кадр.
- Не выполняй блокирующие сетевые операции в Unity main thread.
- Не обращайся к Unity API из фоновых потоков, если API явно не поддерживает это.

## Производительность

- Не создавай лишние аллокации в Update, FixedUpdate и LateUpdate.
- Не используй LINQ в горячих участках без оценки стоимости.
- Не выполняй поиск объектов сцены каждый кадр без необходимости.
- Используй кеширование reflection и Unity-компонентов с корректной инвалидацией.
- Разделяй частоту симуляции, частоту сетевой отправки и частоту рендеринга.
- Не оптимизируй предположительные проблемы ценой усложнения архитектуры без измерений.

## Работа с ванильной игрой

- Не выдумывай методы, поля и поведение игровых классов.
- Проверяй сигнатуры и тела методов по декомпилированным сборкам.
- Фиксируй найденные точки интеграции в документации.
- Не изменяй оригинальные DLL игры.
- Не допускай повторного захвата событий, вызванных применением сетевой реплики.
- Учитывай уничтожение Unity-объектов, смену сцены и повторную инициализацию.

## Обязательный процесс разработки

1. Изучи существующую реализацию и связанные игровые механики.
2. Определи затрагиваемые инварианты и возможные сетевые сбои.
3. Сформулируй минимальный план изменений.
4. Добавь воспроизводимый тест для исправляемого дефекта, если это технически возможно.
5. Реализуй изменения.
6. Выполни сборку и автоматизированные тесты.
7. Проверь изменённый код на нарушения архитектуры и сетевых инвариантов.
8. Выполни доступные интеграционные проверки.
9. Обнови документацию и результаты проверок.

Из каталога `mode/` запускай `powershell.exe -NoProfile -File ./scripts/Verify.ps1` для сборки и автоматизированных проверок. Игровые проверки выполняй отдельно по `docs/verification.md`.

## Критерии завершения

Задача не считается полностью проверенной только потому, что проект компилируется.

В итоговом отчёте указывай:

- Что изменено.
- Какие инварианты сохранены.
- Какие команды проверки реально выполнены.
- Какие тесты прошли или завершились ошибкой.
- Какие игровые сценарии проверены.
- Что осталось непроверенным.
- Какие ограничения и риски сохраняются.

Запрещено выдавать статический анализ или успешную компиляцию за подтверждение работы сетевой механики в игре.

## Владение состоянием и архитектурные границы

Выделение Core не должно ограничиваться переносом вспомогательных функций, проверок и статических методов.

Core должен владеть сетевым состоянием, жизненным циклом операций и правилами переходов состояния.

Unity-адаптеры должны отвечать за взаимодействие с ванильными объектами, выполнение игровых операций и отображение результатов.

Для каждой сетевой механики разделять:

- Авторитетное состояние.
- Клиентское состояние.
- Обработку команд.
- Незавершённые операции.
- Сетевую репликацию.
- Ванильную игровую интеграцию.
- Визуальное представление.

Не хранить сетевое состояние и Unity-объекты в одной записи, если это препятствует независимому тестированию и созданию нескольких сетевых участников.

Не передавать управление всей игровой операцией обратно в инфраструктуру через универсальные делегаты только ради формального отсутствия зависимостей Core от Unity.

Использовать узкие предметные контракты для необходимых ванильных операций.

Учитывать возможность отказа ванильной операции и обеспечивать согласованность между авторитетным состоянием и фактическим игровым результатом.

Не считать перенос методов в отдельную сборку завершённой декомпозицией.

Partial-классы не являются механизмом разделения ответственности.

Не дробить классы исключительно ради уменьшения количества строк.

Каждый компонент должен иметь понятного владельца состояния и определённую причину изменения.

Сетевые идентификаторы участников должны быть независимы от конкретного транспорта. Steam ID является инфраструктурной идентичностью.

При разработке новых механик запрещено увеличивать существующие классы-координаторы за счёт логики, которая должна принадлежать отдельному предметному компоненту.

## Архитектурный образец сетевых механик

Подсистема Core/Items является архитектурным образцом для разработки новых сетевых механик.

При реализации репликации персонажей, мобов, жидкостей, контейнеров, крафта и других сущностей использовать аналогичное разделение ответственности, если оно соответствует предметной области.

- Авторитетное сетевое состояние принадлежит Core.
- Клиентское сетевое состояние изолировано от авторитетного.
- Host и Guest имеют отдельные компоненты, если их обязанности существенно различаются.
- Unity-интеграция осуществляется через узкие предметные контракты.
- Ванильные операции выполняются через адаптеры.
- Репликация и сериализация не должны зависеть от Unity-объектов.
- Визуальное представление не является источником авторитетного состояния.
- Каждая новая коллекция должна иметь определённый жизненный цикл и стратегию ограничения размера.
- Каждое состояние ожидания сетевого ответа должно иметь определённый механизм завершения, таймаута или восстановления.
- Массовые сетевые операции должны учитывать бюджет обработки и отправки за игровой тик.
- Не допускать неограниченного накопления удалённых сущностей, квитанций операций и незавершённых запросов.
- Не копировать структуру подсистемы Items механически, если другая механика имеет более простую модель состояния.

Не проводить повторный глобальный рефакторинг существующей архитектуры без конкретной технической необходимости.


## Игровая тестовая среда

При работе с сетевыми механиками обязательно читать `docs/testing-sandbox.md`, `docs/game-test-api.md`, `docs/scenario-format.md` и `docs/testing-implementation.md`. Существующие Core/Protocol и проверки сохранять. Использовать общий TestKit для NetworkChecks и игрового тестового плагина. Не дублировать production-обработчики, не заменять их заглушками в интеграционных тестах. Один Unity-мир не является несколькими независимыми игровыми мирами. Отдельно сообщать результаты Core, Unity host integration, Unity guest projection и Steam E2E.

Сценарии должны быть воспроизводимыми, иметь seed, ограниченный таймаут, независимые наблюдения и машинно-читаемый отчёт. Setup не должен выполнять проверяемое действие. Нельзя подменять реальные действия прямой записью авторитетного состояния или копировать состояние хоста в клиентский реестр. Неподдерживаемые механики отмечать BLOCKED, не PASS. При исправлении сетевого дефекта добавлять регрессионный сценарий. Сохранять визуальный режим наблюдения, не влияющий на критерии проверки. Не изменять оригинальные сборки, пользовательские сохранения и настройки; тестовый режим только явно включённый, без Steam lobby. Не распространять тестовые сборки с production. После изменений запускать Verify.ps1 и доступные игровые сценарии; фиксировать реальные команды и результаты.
